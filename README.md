# vaultwarden-restore-drill

Бэкапы self-hosted менеджера паролей [Vaultwarden](https://github.com/dani-garcia/vaultwarden), которые не просто копируются, а **каждый день автоматически восстанавливаются и проверяются**. Если бэкап не сделан или из него не поднимается сервис — приходит алерт в Telegram.

> 🚧 **В работе: готовы этапы 0–4 из 6.** Каждую ночь бэкап снимается с VPS, проверяется и **восстанавливается в одноразовом контейнере**; при любом сбое — алерт в Telegram. Дальше — метрики, дашборд и алерт «бэкап устарел».

## Зачем

В сентябре 2026 года бэкапы моего Vaultwarden три недели почти не работали: **3 удачных дня из 23**, самый длинный перерыв — 10 дней. Скрипт был, таймер был, а проверок и алертов не было — узнал я об этом случайно, через 22 дня.

Разбор: [postmortem](docs/postmortems/2026-09-02-silent-backup-failures.md).

Бэкап, из которого ни разу не восстанавливались, — это не бэкап, а надежда. Цель проекта — превратить её в проверяемый факт с цифрами.

## Как устроено

```
VPS (Vaultwarden в rootless Podman)          Pi (пользователь vwbackup, таймер 03:30)
                                      ssh
vaultwarden backup → снимок базы   ◄──────── ключ Pi: только этот скрипт,
+ rsa_key.pem + attachments/                  только с адреса Pi, без терминала
→ tar.gz в stdout                  ────────► проверки: gzip, tar, integrity_check
                                              → snapshots/<UTC-время>.tar.gz, 30 дней
                                   при любом сбое: OnFailure= → Telegram (через SOCKS-прокси)

04:00 restore drill: распаковать → integrity_check → записи на месте → Vaultwarden той же
      версии в контейнере без сети → /alive; любой сбой → Telegram
(этап 5) метрики → Prometheus → Alertmanager, алерт «бэкап устарел», дашборд Grafana
```

- VPS: [`vps/vw-backup-export`](vps/vw-backup-export) — делает снимок и отдаёт архив.
- Pi: [`scripts/backup.sh`](scripts/backup.sh) — забирает, проверяет, хранит; [`scripts/restore-drill.sh`](scripts/restore-drill.sh) — проверка восстановления; [`scripts/notify-telegram.sh`](scripts/notify-telegram.sh) — алерт; [`systemd/`](systemd/) — сервисы и таймеры.
- Установка: [`docs/install.md`](docs/install.md).

## Что проверено

- 3 запуска подряд — у всех трёх снимков `PRAGMA integrity_check` = `ok`.
- VPS недоступен → бэкап падает с ошибкой, в `snapshots/` ничего не появляется.
- Ключ бэкапа: на просьбу выполнить `cat /etc/passwd` VPS отдаёт архив бэкапа; проброс порта и терминал запрещены.
- Оборванная передача не оставляет на VPS временных файлов. Этот тест нашёл настоящий баг — [исправление](https://github.com/Kernyx/vaultwarden-restore-drill/commit/1e8461a).
- Специально сломанный бэкап → Telegram принял алерт через 480 мс. Первый прогон этого теста нашёл баг: сервис алерта сам падал до отправки — [исправление](https://github.com/Kernyx/vaultwarden-restore-drill/commit/0059ada).
- Проверка восстановления на настоящем бэкапе проходит, а на специально испорченных копиях падает — каждая на своём шаге:

  | Испорченный бэкап | Где остановилась проверка |
  |---|---|
  | обрезанный архив | не распаковался |
  | испорчены страницы базы | `database disk image is malformed` |
  | удалены все записи | `empty vault` |
  | удалена треть записей | `items dropped from 777 to 512` |
  | удалена таблица миграций: база цела, но приложение на ней не стартует | `did not come up` |

  Последний случай ловит только запуск самого приложения — `integrity_check` и подсчёт записей его пропускают.

## Решения и компромиссы

| Решение | Почему | Цена |
|---|---|---|
| Бэкапы хранит Pi, а не ноутбук | Pi включён всегда и стоит в другом месте, чем VPS | SD-карта — не самый надёжный носитель; копия пока одна |
| Pi сам забирает бэкап (pull) | У VPS нет доступа к бэкапам: взлом VPS их не сотрёт | Pi хранит ключ к VPS — поэтому ключ ограничен (строка ниже) |
| Ключ с `from=`, `restrict`, `command=` | Ключ умеет только одно — получить бэкап, и только с адреса Pi | Если сменится адрес Pi в tailnet, бэкап упадёт (заметит алерт) |
| Встроенная `vaultwarden backup` вместо копирования файлов | Согласованный снимок без остановки сервиса | Скрипт разбирает текст вывода команды; если формат изменится — экспорт упадёт громко, а не тихо |
| tar.gz по SSH вместо rsync | Проще, и ключ легко ограничить | Каждый раз передаётся всё; при 480 КБ неважно, при гигабайтах вложений — пересмотреть |
| Сначала проверка, потом `mv` | В `snapshots/` только проверенные архивы, пустых и битых папок больше нет | — |
| Отдельный пользователь и песочница systemd | Скрипт без sudo и может писать только в свою папку | Чуть больше шагов установки |
| Алерт через `OnFailure=` | systemd сам запускает алерт при любом сбое: код ошибки, таймаут, падение | Промолчит, если бэкап вообще не запустился — это закроет алерт «бэкап устарел» (этап 5) |
| Telegram через SOCKS-прокси | API Telegram заблокирован из сети Pi, а Telegram всегда под рукой | Алерт зависит от прокси: упадёт прокси — алерт не уйдёт |
| Проверка восстановления запускает само приложение | Только так видно, что данные реально поднимаются: целая с точки зрения SQLite база ещё не значит рабочий сервис | Нужен образ Vaultwarden на Pi (316 МБ) |
| Контейнер без сети, read-only, без capabilities, от `nobody` | Проверка ничего не может отправить наружу и почти ничего не может сломать | Живость проверяется изнутри контейнера скриптом из самого образа |
| Rootful Podman | Тот же Podman, что на VPS; без демона; просто запустить из systemd | Скрипт проверки работает от root (rootless — в «Что плохо») |
| Версия Vaultwarden — из манифеста бэкапа | Восстанавливаем той же версией, что писала данные | При обновлении на VPS нужен доступ к Docker Hub |
| Порог «минус 20% записей» | Стёртое или зашифрованное хранилище выглядит как резкая потеря записей | Массовое удаление руками тоже поднимет тревогу — тогда удалить `last.env` |
| `DynamicUser` + `LoadCredential` для алерта | Одноразовый пользователь; токен не виден ни в окружении, ни в `ps` | Из такой песочницы не работает `systemctl` — нашли тестом, данные берём из `$MONITOR_*` |

## Что плохо сейчас

- Если бэкап вообще не запустится (Pi выключен, таймер отключён), `OnFailure=` промолчит — нужен алерт на отсутствие успеха (этап 5).
- Алерт зависит от прокси Throne, а тот стартует только вместе с графической сессией Pi.
- Если не дойдёт сам алерт (нет прокси или Telegram), останется только запись в журнале.
- Проверка не входит в хранилище: она доказывает, что приложение поднялось на данных, но не что записи расшифровываются. Следующий шаг — тестовая учётная запись-«канарейка» и вход через Bitwarden CLI.
- Проверка восстановления работает от root (rootful Podman). Rootless-вариант под `vwbackup` сложнее с systemd — пока не сделан.
- Копия одна, на SD-карте Pi.
- Архивы на Pi не зашифрованы. Записи в хранилище паролей зашифрованы самим Bitwarden, но `rsa_key.pem` лежит как есть — защищён только правами `0600`.
- На VPS образ `vaultwarden/server:latest` — версия может смениться незаметно.
