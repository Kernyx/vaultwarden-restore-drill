# vaultwarden-restore-drill

Бэкапы self-hosted менеджера паролей [Vaultwarden](https://github.com/dani-garcia/vaultwarden), которые не просто копируются, а **каждый день автоматически восстанавливаются и проверяются**. Если бэкап не сделан или из него не поднимается сервис — приходит алерт в Telegram.

> 🚧 **В работе.** Сейчас в репозитории исходная версия бэкапа — как было до проекта — и разбор реального сбоя. Прогресс — в разделе «План».

## Зачем

В сентябре 2026 года бэкапы моего Vaultwarden три недели почти не работали: **3 удачных дня из 23**, самый длинный перерыв — 10 дней. Скрипт был, таймер был, а проверок и алертов не было — узнал я об этом случайно, через 22 дня.

Разбор: [postmortem](docs/postmortems/2026-09-02-silent-backup-failures.md).

Бэкап, из которого ни разу не восстанавливались, — это не бэкап, а надежда. Цель проекта — превратить её в проверяемый факт с цифрами.

## Как будет устроено

```
VPS:  vaultwarden → sqlite3 .backup → снимок базы
        │ rsync по Tailscale — Pi забирает данные сам (pull)
        ▼
Pi:   snapshots/ → restore drill: одноразовый контейнер vaultwarden
                   (поднялся? база цела? записи на месте? за сколько секунд?)
        │ метрики
        ▼
      Prometheus → Alertmanager → Telegram      Grafana — дашборд
```

## Что плохо сейчас

Исходная версия лежит в [`scripts/`](scripts/) и [`systemd/`](systemd/) без изменений — чтобы по истории коммитов было видно, что и почему поменялось.

- Живая база SQLite копируется по файлам вместе с WAL-журналом — копия может оказаться несогласованной.
- Ни одного алерта: systemd помечает сервис `failed`, но об этом никто не узнаёт.
- Папка бэкапа создаётся до скачивания данных — пустые папки маскируют сбои.
- Бэкап-хост — ноутбук: часто выключен и зависит от Tailscale на нём.
- Восстановление ни разу не проверялось.
